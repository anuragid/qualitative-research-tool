## Executive summary

Today's live-investigation session exposed five production bugs in rapid succession. Three were fixed in surgical PRs (#14, #17, #18). Two more were discovered during verification and are the subject of this phase, plus three additional improvements that the user approved as part of the "production-grade" reframe.

The root problem in every case is the same: **methodex's state machines are strings in a database, written from twenty places, with no enforced invariants and no owner.** Today's scaling refactor (Wave 1+2, 2026-04-06) solved the *capacity* problem. Phase 1 solves the *correctness* problem, deploy-safety problem, and frontend-robustness problem. Phase 2 will solve the *observability* problem.

**Primary trade-off:** This phase trades ~1 day of focused multi-PR work for the elimination of the entire class of bugs we saw today. No infrastructure changes, no stack changes. Only tightening what's already there.

## Goals

1. **Every Railway deploy is invisible to end users.** No stuck videos, no 5xx spikes, no "analyzing" state that needs the watchdog to reset.
2. **Retry always works.** Clicking "Retry Analysis" on an errored video dispatches a new chain that runs to completion, not one that silently skips.
3. **Transcription → analysis is automatic.** The user clicks "Transcribe" once. Once transcription finishes, the analyze chain dispatches automatically. No gap where `video.status="transcribed"` but `video_analyses` has no row.
4. **The frontend never crashes on an unexpected API response shape.** Every data-display component tolerates missing/null/partial data and renders an empty state or error boundary, never a React crash.
5. **(Stretch) No code outside a centralized state module writes `video.status = "X"` or `project.status = "X"`.** Enums at the schema level, transition table in the state module.

## Non-goals (explicit scoping)

- **Observability stack, staging env, canaries, alerts.** These are Phase 2. Do not add Prometheus, Grafana, request-ID middleware, new Sentry breadcrumbs beyond what fits naturally inside these PRs, or new alert rules. Each is its own PR in Phase 2.
- **Load testing or query profiling.** Phase 3.
- **New features.** This phase is purely correctness + robustness. Do not add any user-visible capability, UI affordance, or API surface. If a PR tempts you to add "while I'm here, let me also...", stop.
- **Retry history / audit trail.** Not today. The retry fix resets the row rather than preserving the old attempt.
- **Postgres-level enum type migration for `VideoStatus` etc.** PR #22 (stretch) uses Python `enum.Enum` + `Column(Enum(VideoStatus))` which is SQLAlchemy's choice-enforced-at-write pattern. Migrating to a native Postgres ENUM type is a separate decision (reversibility, migration complexity) and is deferred.

**Derived problem:** every Railway deploy SIGTERMs the worker after 60s, killing in-flight chain steps that take 1-5 min each. Those tasks go to Redis `unacked` and sit there for up to 3600s. Meanwhile the watchdog at 35 min stamps them `errored`. Net: every deploy creates a 35-min window of errored videos.

**Proven in production today:** Kathleen video `4b1f4b25-c94f-4bf8-9a6a-0958ddfc4e41` was in EXPLAIN step at 18:25:46 UTC when PR #14 deployed at 18:26:34. Her task `ab793cc0-218e-49fd-8362-903f3bdf2998` sat in Redis `unacked` until it was re-delivered at **19:27:14** — exactly 3600s later — by which time the watchdog had already stamped her `errored` at 18:52:58. The re-delivered task saw `VideoAnalysis.status == "error"` and silently short-circuited via the defensive "skip if errored" check.

### The retry-swallow bug (newly discovered 20:00 UTC)

After Kathleen was watchdog-errored, I asked the user to click "Retry Analysis" to verify Fix C worked. The retry fired at 20:00:24 UTC (confirmed in worker logs — all 5 chain steps received within 150ms). But every single step logged `"Skipping <step> for 4b1f4b25... — already in error state"` and exited immediately. No work done. The chain completed as a no-op. Three minutes later the watchdog re-swept and found `video.status="analyzing"` with `VideoAnalysis.status="error"` — an impossible state — and stamped the video `error` again.

**Root cause:** `backend/app/routes/videos.py:622-624` resets `video.status = "analyzing"` and `video.error_message = None` in the request transaction before dispatching. It does **not** reset the `VideoAnalysis` row's `status` field. The chain's defensive skip-if-errored check (in each step task, checking `VideoAnalysis.status`) then short-circuits every step.

The defensive skip is correct for preventing double-execution during normal chain flow. It is wrong for the retry path. Either the retry must reset the analysis row, or the skip check must distinguish "errored-and-retrying" from "errored-and-done."

### The transcribe → analyze gap

After transcription completes (`backend/app/tasks/transcription_tasks.py` check_transcription_task success branch, around line 220), the code sets `video.status = "transcribed"` and stops. The user must manually click "Analyze" on each video to dispatch the chain. In the interim window, `videos.status = "transcribed"` exists but `video_analyses` has no row, which was the 404 → frontend crash that Fix C patched defensively. The proper fix is auto-dispatch.

### The frontend defensive-rendering gap

Fix C added `?? []` guards to 5 files that were crashing. There are ~40 more `.map(` and `.length` call sites across `frontend/src/components/analysis/`, `frontend/src/components/videos/`, `frontend/src/components/projects/` that have never been audited. Any change in API response shape (e.g., PR #22's enum serialization) risks crashing them. Also, there's no runtime schema validator between the API response and the components — TypeScript types are compile-time only.

### State-machine write sites

Grep confirms ~20 distinct sites in the codebase that write `video.status = X`, `project.status = X`, `video_analysis.status = X`, or `transcript.status = X` directly. File list:

- `backend/app/routes/videos.py` (multiple — analyze, transcribe, per-step retry routes)
- `backend/app/routes/projects.py` (cross-video analyze)
- `backend/app/tasks/analysis_steps.py` (all 5 step tasks + `_update_analysis_error`)
- `backend/app/tasks/project_analysis_steps.py` (cross-video steps)
- `backend/app/tasks/transcription_tasks.py` (transcribe_video_task, check_transcription_task)
- `backend/app/tasks/pipeline_errors.py` (`handle_pipeline_error`, `handle_project_pipeline_error`)
- `backend/app/tasks/watchdog_tasks.py` (4 branches)
- `backend/app/services/project_state_service.py` (`update_project_state_for_completion`)

This scattered-write pattern is why Bug B (the `ready`-gate trap) existed: the writer at one site forgot that another site's gate excluded its state.

#### PR #19.5 — Retry-swallow fix

**Goal:** Clicking "Retry Analysis" on an errored video actually runs the chain.

**Files:** `backend/app/routes/videos.py` (analyze route body), `backend/tests/test_analyze_retry.py` (new or extend existing).

**Brief:** `prs/pr19-5-retry-swallow.md`

**Summary of changes:**
- In the `/videos/{id}/analyze` POST handler, after setting `video.status = "analyzing"` and clearing `error_message`, also reset the `VideoAnalysis` row if it exists and its status is `"error"`. Set `status = "pending"`, clear all `*_completed_at` fields, clear `step_status`, clear `chunks`/`inferences`/`patterns`/`insights`/`design_principles` jsonb fields.
- Do the reset inside the same DB transaction as the `video.status` write, so either both happen or neither does.
- The chunk step is idempotent and will re-populate `chunks` etc. on its first pass.
- Add test: create a video with `VideoAnalysis.status = "error"`, call the analyze route, assert the row is reset AND the chain is dispatched AND the chain steps do NOT skip.

**Acceptance:** Kathleen (or any errored video) can be retried via the API and runs to completion without manual DB intervention. Regression test verifies the retry-swallow case specifically.

#### PR #20 — Auto-dispatch analyze after transcription

**Goal:** Eliminate the manual "Analyze" click after "Transcribe". Eliminates the `transcribed-but-no-analysis-row` intermediate state where most of today's UI bugs lived.

**Files:** `backend/app/tasks/transcription_tasks.py` (check_transcription_task success branch), `backend/tests/test_auto_dispatch_analyze.py` (new).

**Brief:** `prs/pr20-auto-dispatch.md`

**Summary of changes:**
- At the end of `check_transcription_task` when transcription status flips to `completed`, automatically dispatch the analyze chain using the same chain signature as `routes/videos.py:639-645`.
- Guard with an idempotency check: do not dispatch if `video.status` is already `analyzing` (another chain is running) or `analyzed` (already done) or if a `VideoAnalysis` row exists with `status in ("processing", "completed")`.
- Leave the manual POST `/videos/{id}/analyze` endpoint in place as a retry affordance (PR #19.5 makes it work).
- Consider: should the user still see a button? Yes — keep the Analyze button visible, but it becomes a "Re-run analysis" affordance rather than a required step. Frontend changes are out of scope for this PR; leave the button where it is.

**Acceptance:** User uploads a video, transcribes it, and walks away. When they return, analysis is either in progress or complete. No click-Analyze-again gap.

#### PR #21 — Frontend defensive rendering + zod schemas

**Goal:** The frontend never crashes on a valid API response. Schema drift is contained as a clear error, not a React crash.

**Files:** `frontend/src/schemas/` (new directory with zod schemas), `frontend/src/services/api.ts` (wrap every response with schema validation), `frontend/src/components/analysis/*.tsx` (codemod `.map(` and `.length`), `frontend/src/components/videos/*.tsx` (same), `frontend/src/components/projects/*.tsx` (same), `frontend/src/components/ErrorBoundary.tsx` (extend if needed), `frontend/src/types/index.ts` (derive types from zod schemas).

**Brief:** `prs/pr21-frontend-defensive.md`

**Summary of changes:**
- Install `zod` (already may be available — check `package.json`)
- Create one zod schema per API response shape: `VideoAnalysisSchema`, `ProjectAnalysisSchema`, `VideoSchema`, `ProjectSchema`, `TranscriptSchema`, `WordLevelTranscriptSchema`. Derive TS types via `z.infer<>`.
- Each API call in `services/api.ts` runs the response through `schema.parse()`. A parse failure gets sent to Sentry with the unexpected shape as extra data, and rendered as a user-visible toast `"Something unexpected came back from the server — please refresh."`
- Codemod every `.map(` in the three component directories to use `(items ?? []).map(...)`
- Codemod every `.length` access on optional arrays to `(items?.length ?? 0)`
- Wrap each top-level route component in an error boundary that shows a `<SomethingWentWrong />` component (create one if it doesn't exist) with a Refresh button
- Add a unit test per schema with a "valid" fixture and an "invalid shape" fixture

**Acceptance:** Take the Sentry JAVASCRIPT-REACT-6 culprit video (`b3e8f956-...`) and force an API response with missing `how_might_we` field. The frontend must NOT crash — it shows an error toast or an empty state. Automated: a Playwright test (if Playwright is already in the repo) that mocks an empty response and asserts no React error boundary fires.

### Wave B — sequential, stretch

#### PR #22 — Status enums + centralized state machine (stretch goal)

**Goal:** Eliminate the class of bug we saw today by making illegal state writes impossible.

**Files:** `backend/app/state/` (new package with `video_state.py`, `project_state.py`, `analysis_state.py`, `transcript_state.py`, `events.py`), `backend/app/models/database_models.py` (switch `Column(String)` → `Column(Enum)` on all 4 status fields), an Alembic migration, and ~20 call-site edits across the routes + tasks + services identified in the "State-machine write sites" section above.

**Brief:** `prs/pr22-state-machine-enums.md`

**Summary of changes:**
- Define 4 Python `enum.Enum` classes with the exact string values currently in the DB: `VideoStatus`, `VideoAnalysisStatus`, `ProjectStatus`, `TranscriptStatus`.
- Define 4 `StateMachine` classes with explicit transition tables. Illegal transitions raise `InvalidTransitionError`.
- Alembic migration: `ALTER TABLE videos ALTER COLUMN status TYPE ...`. Keep existing string values; only enforce at the SQLAlchemy layer (`Column(Enum(VideoStatus))`) to avoid a destructive DB migration. Native Postgres ENUM type is a future spec.
- Rewrite every direct write site to call `VideoStateMachine.transition(video, Event.X)` etc.
- Tests: one positive + one negative test per state transition.

**Acceptance:** Bug B (the `ready` gate trap) becomes impossible — it would fail a unit test in the new state module. Running the full backend suite is green. Running an end-to-end smoke test through the chain still works.
