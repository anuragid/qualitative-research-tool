## Executive summary

Methodex is currently running on Railway Hobby with single-replica backend and worker services. At low load it works, but the architecture has three issues that will bite under classroom peak load:

1. **The video analysis pipeline pins a worker thread for 2–3 minutes per video** because all 5 LLM-calling steps run sequentially inside one Celery task. A single student analyzing a video occupies one of only 8 worker threads for the entire duration, and a crash mid-pipeline loses all work done so far.
2. **Celery Beat is embedded in the worker service**, which blocks horizontal scaling — adding worker replicas would cause every scheduled task to fire once per replica.
3. **Both the backend and worker run on a single replica**, so a container crash or a deploy produces user-visible errors for ~30 seconds.

This spec fixes all three on the Hobby plan (no upgrade to Pro). Railway Hobby actually supports up to **6 replicas per service** and **48 vCPU / 48 GB burst per container** — verified directly via the Railway GraphQL API — so there's ample headroom for target-B load without paying for Pro. The work is organized into six independent tracks (T1–T6) that can be executed in parallel worktrees with dedicated subagents.

**Primary trade-off:** This plan increases monthly Railway spend from ~$5.45 to ~$7.65 (+40%, +$2.20/mo). Current credit balance of $45.88 absorbs this trivially. In exchange we get redundancy, graceful burst handling, and ~3–5× more effective worker throughput under peak load.

## Goals

1. Serve target B (~100 users, ~25 concurrent video analyses at peak) on the Hobby plan without queueing visible to students. Headroom to burst to 40+ without user-facing slowdown.
2. Eliminate single-points-of-failure at the container level — a crash or deploy on any one container should not produce user-visible errors.
3. Reduce per-video wall-clock time under load by breaking the pipeline's thread-pinning bottleneck.
4. Trim idle memory footprint enough that a 2-replica topology comfortably fits within the current cost envelope.
5. Structure the work so it can be executed in parallel by independent subagents in separate worktrees.

## Non-goals (explicitly out of scope)

- **Postgres backups.** Hobby lacks automated volume backups (`maxBackupsCount: 0`). This is a real concern but is explicitly deferred to a separate future spec (not yet written; placeholder name `docs/superpowers/specs/YYYY-MM-DD-postgres-backup-system-design.md`). Do not bundle backups into this spec's implementation — it was an explicit scoping decision during brainstorming.
- **Async SQLAlchemy / asyncpg migration.** Deep refactor, high risk, unnecessary at target-B scale. Revisit if we ever need target C (300+ users).
- **Multi-region deploys.** Not supported on Hobby, and not needed for the current Chicago-based cohort.
- **Pro plan upgrade.** Deferred unless we discover a blocker we can't engineer around on Hobby.
- **Observability upgrade beyond current Sentry.** Sentry + Railway logs (7-day retention) are sufficient at this scale.
- **Intra-step chord parallelism** for `infer_node`. The current `infer_node` sends all chunks in a single LLM call (verified in `backend/app/agents/nodes/infer.py:71`), so there's no natural parallelism to extract without changing prompt semantics.
- **Chain cancellation API.** If a user wants to cancel mid-analysis (rare), they still have to wait for the watchdog after this work lands.

### Capacity numbers (steady state, Hobby plan)

| Service | Replicas | Per-replica | Total capacity | Headroom within Hobby |
|---|---|---|---|---|
| backend | 2 | uvicorn × 2 workers | 4 concurrent requests | Scale to 6 replicas → 12 |
| worker | 2 | Celery threads × 16 | 32 concurrent tasks | Bump concurrency to 24 → 48 |
| beat | 1 | Beat scheduler only | N/A | Never scales |
| Postgres | 1 | Railway plugin | — | Single instance at this scale |
| Redis | 1 | Railway plugin | — | Single instance at this scale |

### Why this topology meets target B

- 25 concurrent analyses need ~25 worker threads. We have 32. After the T1 pipeline chain refactor, those 32 slots cycle through much shorter tasks, so effective throughput is 3–4× higher than raw slot count suggests.
- 25 concurrent users polling status + dashboard ≈ 25–50 req/sec on the API. We have 4 concurrent handlers × ~100 req/sec per handler = ~400 req/sec capacity. ~8× headroom.
- If any one replica dies, the other takes full traffic while Railway rolls the crashed one in the background. No user-visible outage.
- Beat has exactly one instance, so scheduled tasks fire exactly once per schedule regardless of how many worker replicas are running.

## Track-by-track design

The work is split into six independent tracks so they can be executed in parallel worktrees by dedicated subagents.

### T1 — Celery chain refactor (the biggest code change)

**Problem.** `analyze_video_task` in `backend/app/tasks/analysis_tasks.py:266-487` runs all 5 analysis nodes sequentially inside one function (`_run_video_pipeline`), pinning one Celery thread for the entire 1–4 minute pipeline. A crash mid-pipeline loses all work done so far. `analyze_project_task` in the same file has the same problem for the 3-node cross-video pipeline.

**Solution.** The `/videos/{id}/analyze` route dispatches a **Celery chain** of the 5 per-step tasks that already exist in `backend/app/tasks/analysis_steps.py`. Each step runs as its own Celery task; when one finishes, Celery automatically queues the next; the worker thread is released between steps so other tasks can run.

#### Chain dispatch with immutable signatures

Celery chains normally pass the previous task's return value as the first argument to the next task. We don't want that — each step should get its own explicit `(video_id, user_id)`. The `.si()` (immutable signature) method does this:

```python
# backend/app/routes/videos.py — replacing analyze_video_task.delay(...)
from celery import chain
from app.tasks.analysis_steps import (
    analyze_chunk_step,
    analyze_infer_step,
    analyze_relate_step,
    analyze_explain_step,
    analyze_activate_step,
)
from app.tasks.pipeline_errors import handle_pipeline_error

pipeline = chain(
    analyze_chunk_step.si(str(video_id), current_user_id),
    analyze_infer_step.si(str(video_id), current_user_id),
    analyze_relate_step.si(str(video_id), current_user_id),
    analyze_explain_step.si(str(video_id), current_user_id),
    analyze_activate_step.si(str(video_id), current_user_id),
).on_error(handle_pipeline_error.s(video_id=str(video_id)))

result = pipeline.apply_async()
# Response shape stays identical so frontend is untouched:
return {
    "message": "Video analysis task started",
    "video_id": str(video_id),
    "analysis_id": str(video_analysis.id),
    "task_id": result.id,
    "status": "processing",
}
```

Same pattern for project analysis, using 3 new per-step tasks that mirror the existing video step pattern (see T1.4 below).

#### Step tasks stay almost identical to today

`backend/app/tasks/analysis_steps.py` already defines each of the 5 video steps as an independent Celery task. Each step:
- Takes `(video_id, user_id)` as args
- Loads state fresh from the database on each call
- Runs exactly one analysis node
- Saves partial results (`chunks`, `inferences`, `patterns`, `insights`, `design_principles`)
- Updates `step_status` dict on the `VideoAnalysis` row
- Has `autoretry_for=(Exception,)` + `dont_autoretry_for=(NonRetryableAnalysisError,)` + exponential backoff

**Changes to each step task:**

1. **Add a cancellation precheck** at the top of each step task:
   ```python
   # Read fresh state; if watchdog or earlier step marked error, skip
   self.db.expire_all()
   analysis = self.db.query(VideoAnalysis).filter(
       VideoAnalysis.video_id == UUID(video_id)
   ).first()
   if analysis is None or analysis.status == "error":
       logger.info(f"Skipping {step_name} for {video_id} — already in error state")
       return {"video_id": video_id, "status": "skipped"}
   ```
   This keeps subsequent chain links from doing redundant work after a halt.

2. **Move initial-state setup into `analyze_chunk_step`.** Today some of the "create `VideoAnalysis` row if missing, set `status=processing`, initial `step_status` dict" logic lives in the route; move it fully into the chunk step task so the route is just a dispatcher.

3. **Terminal state transition stays in `analyze_activate_step`.** It already does this correctly.

No changes to the retry decorators — the existing `autoretry_for` + `dont_autoretry_for` pattern works as-is.

#### New file: `backend/app/tasks/pipeline_errors.py`

A single task that Celery calls via `.on_error()` when any link in the chain fails:

```python
@celery_app.task(name="handle_pipeline_error", base=DatabaseTask, bind=True)
def handle_pipeline_error(self, request, exc, traceback, video_id: str):
    """Chain error handler. Idempotent — safe to run after a step's own
    except block has already marked the analysis as error.
    """
    from app.tasks._pipeline_utils import sanitize_error, build_error_json

    try:
        self.db.rollback()
        video = self.db.query(Video).filter(Video.id == UUID(video_id)).first()
        analysis = self.db.query(VideoAnalysis).filter(
            VideoAnalysis.video_id == UUID(video_id)
        ).first()

        # request.task contains the task name that raised
        failed_step = getattr(request, "task", "unknown").split(".")[-1] if request else "unknown"
        error_json = build_error_json(
            step=failed_step,
            exc=exc,
            message=sanitize_error(str(exc)),
        )

        if video and video.status not in ("error", "analyzed"):
            video.status = "error"
            video.error_message = error_json
        if analysis and analysis.status != "error":
            analysis.status = "error"
            analysis.completed_at = datetime.now(timezone.utc)

        self.db.commit()
    except Exception as e:
        logger.error(f"handle_pipeline_error itself failed: {e}")
        try:
            self.db.rollback()
        except Exception:
            pass
```

#### Failure-mode matrix

| Scenario | Today | After T1 |
|---|---|---|
| Retryable LLM error mid-pipeline | In-function retry × 2, then raise | Per-task retry × 3 with exponential backoff, chain auto-halts if retries exhausted |
| Non-retryable error (validation, permanent LLM fail) | `NonRetryableAnalysisError` raised, halts | Same — `dont_autoretry_for` prevents retries, chain halts immediately |
| Watchdog marks analysis stuck | `_is_cancelled` poll catches it between nodes | Next step's cancellation precheck catches it; chain halts |
| Worker crashes mid-step | `task_acks_late` + `task_reject_on_worker_lost` → re-queued on another replica | Same behavior — but now 2 worker replicas, so re-queue is fast and no single-point-of-failure |
| User deletes video mid-analysis | FK cascade; next step hits missing row → raises | Same |
| Entire pipeline succeeds | Final `activate_node` sets `video.status = "analyzed"` | Same |

### T2 — Beat extraction + multi-replica topology

#### Beat extraction

**Problem.** Celery Beat is embedded in the worker via `--beat` in `backend/scripts/startup.sh:127`. Running 2+ worker replicas with embedded beat would fire scheduled tasks once per replica (watchdog every 2.5 min instead of 5, model validator twice every 6h).

**Solution.** Extract Beat into its own dedicated Railway service. Hard-pinned to `numReplicas=1` forever.

**Changes:**

1. **New Railway service** `beat`, created via the GraphQL API. Same Dockerfile as worker (`backend/Dockerfile.railway`), same environment variables, but with `SERVICE_TYPE=beat` and an overridden start command.

2. **`backend/scripts/startup.sh`** — add a third branch:
   ```sh
   elif [ "$SERVICE" = "beat" ]; then
       echo "⏰ Starting Celery beat scheduler..."
       exec celery -A app.tasks.celery_app beat --loglevel=info
   ```

3. **Worker startup loses `--beat`.** The worker becomes a pure task executor:
   ```sh
   exec celery -A app.tasks.celery_app worker \
       --pool=threads \
       --concurrency=${CELERY_CONCURRENCY:-16} \
       --loglevel=info \
       --without-heartbeat --without-mingle --without-gossip \
       -Q analyze,transcribe,celery
   ```

4. **`CELERY_CONCURRENCY=16`** env var set on worker service (today unset; defaults to 8 in the current `startup.sh`).

#### Backend horizontal scaling

5. **`backend/scripts/startup.sh`** — add `--workers 2` to uvicorn:
   ```sh
   exec uvicorn app.main:app --host 0.0.0.0 --port ${PORT:-8000} \
       --workers 2 --proxy-headers --forwarded-allow-ips='*'
   ```

6. **Railway service config via GraphQL** (scripted, not dashboard-clicked):
   - `backend`: `numReplicas=2`, `healthcheckPath=/health/ready`, `healthcheckTimeout=10`, `drainingSeconds=30`
   - `worker`: `numReplicas=2`, `drainingSeconds=60` (let in-flight tasks finish gracefully)
   - `beat`: `numReplicas=1` (hard), `drainingSeconds=10`

#### Database pool resizing

**Problem.** `backend/app/database.py` today sets `pool_size=10, max_overflow=20` for both the backend and worker. With the new topology, connection math is:
- backend: 2 uvicorn workers × 2 replicas × (pool_size + max_overflow) = significant growth
- worker: 2 replicas × (pool_size + max_overflow) = significant growth
- Naive setting could exhaust Railway's default `max_connections=100` on Postgres

**Solution.** Make `database.py` environment-aware via `SERVICE_TYPE`:

```python
# backend/app/database.py
import os

_SERVICE_TYPE = os.environ.get("SERVICE_TYPE", "api")

# Pool sizes per service type, chosen so total connections across all
# replicas fit comfortably under Postgres max_connections=100
_POOL_CONFIG = {
    "api":    {"pool_size": 5, "max_overflow": 5},   # × 2 workers × 2 replicas = 40
    "worker": {"pool_size": 4, "max_overflow": 4},   # × 2 replicas = 16
    "beat":   {"pool_size": 1, "max_overflow": 1},   # ~2 total
}
_pool = _POOL_CONFIG.get(_SERVICE_TYPE, _POOL_CONFIG["api"])

engine = create_engine(
    settings.DATABASE_URL,
    connect_args=_connect_args,
    pool_pre_ping=True,
    pool_size=_pool["pool_size"],
    max_overflow=_pool["max_overflow"],
    pool_recycle=1800,
    echo=settings.DEBUG,
)
```

Total max concurrent connections: ~58, comfortably under Postgres's 100.

#### Healthcheck endpoints

**Problem.** Today `/health` in `backend/app/main.py:246` is a static 200 that doesn't verify DB or Redis connectivity. Railway has no way to take a broken replica out of rotation.

**Solution.** Split into liveness and readiness endpoints:

```python
@app.get("/health/live")
async def health_live():
    """Liveness — am I running?"""
    return {"status": "alive"}

@app.get("/health/ready")
async def health_ready(db: Session = Depends(get_db)):
    """Readiness — should I receive traffic?"""
    try:
        db.execute(text("SELECT 1"))
    except Exception:
        return JSONResponse(status_code=503, content={"status": "db_down"})
    try:
        # Redis ping via the Celery broker connection
        from app.tasks.celery_app import celery_app
        celery_app.broker_connection().ensure_connection(max_retries=1)
    except Exception:
        return JSONResponse(status_code=503, content={"status": "redis_down"})
    return {"status": "ready"}

# Keep /health as an alias of /health/live for backwards compat with any
# existing monitoring
@app.get("/health")
async def health():
    return {"status": "healthy"}
```

Railway's `healthcheckPath` points to `/health/ready` so broken replicas are automatically pulled from the load balancer.

### T4 — Memory footprint + `llm_service` cleanup

**Motivation.** Memory is ~78% of the current monthly bill, and it's almost all idle footprint (modules loaded at import time whether or not they're used). Trimming per-service baseline memory by ~100–200 MB gives us headroom for the 2-replica topology without blowing the cost envelope.

**Changes:**

1. **Delete `langgraph` from `backend/requirements.txt:14`.** Verify with `grep -r "from langgraph\|import langgraph" backend/app` first. The codebase has already moved away from LangGraph's `graph.invoke()` (see the docstring at `backend/app/tasks/analysis_tasks.py:1-12` — "Calls analysis nodes directly in sequence rather than via LangGraph's graph.invoke()..."), so this should be a clean removal. **Savings: ~50 MB per process.**

2. **Lazy-import heavy modules.** Move top-level `import boto3`, `import openai`, `from cryptography.fernet import Fernet`, `from clerk_backend_api import ...` into the functions that actually use them. The backend API process never hits boto3 at all (only workers do), so deferring the boto3 import sheds ~80 MB from backend idle footprint.

   Affected files (move module imports inside functions):
   - `backend/app/services/s3_service.py` — boto3
   - `backend/app/services/llm_service.py` — openai client
   - `backend/app/services/encryption_service.py` — cryptography.Fernet
   - `backend/app/auth.py` or `backend/app/auth_bridge.py` — PyJWT (keep, but ensure only imported in auth path)

3. **Trim Sentry extras.** `sentry-sdk[fastapi,celery,openai]` → `sentry-sdk[fastapi,celery]` in `backend/requirements.txt`. We use OpenRouter with the OpenAI client, but the OpenAI Sentry integration instruments *every* LLM call with detailed traces, which is noisy and not what we need. **Savings: ~15 MB.**

4. **Rename `FREE_MODEL_FALLBACKS` → `STANDARD_MODEL_FALLBACKS`** in `backend/app/services/llm_service.py`. Grep for every reference and update. This is not a free-tier fallback list — it's a list of paid open-source models on OpenRouter we fall back to when the primary is rate-limited.

5. **Fix stale docstrings** in `backend/app/services/llm_service.py`:
   - Around line 199–200: "common with free OpenRouter models" → "common with open-source models on OpenRouter"
   - Around line 296–297: "Free models may return null content" → "Open-source models may return null content"

6. **Measure before/after.** Definition of done for T4 includes a committed benchmark:
   - Run `ps -p $(pgrep -f 'uvicorn\|celery') -o rss,vsz,cmd` on staging before the change; record in spec
   - Same after; record in spec
   - Target: ≥100 MB reduction per backend replica, ≥150 MB per worker replica

**No feature changes. No API changes. No behavior changes. Pure cleanup.**

### T5 — Redis hardening + operational polish

1. **Redis `maxmemory` + eviction policy.** Today Redis has no memory bound. If queued results accumulate or a Celery bug causes leaks, Redis OOMs silently and Celery breaks. Set bounds via the Redis service's `startCommand` override:
   ```
   redis-server --requirepass $REDIS_PASSWORD --save 60 1 \
       --dir $RAILWAY_VOLUME_MOUNT_PATH \
       --maxmemory 300mb --maxmemory-policy allkeys-lru
   ```
   Celery results expire in 10 min per `celery_app.py:50`, so 300 MB is massive headroom.

2. **Remove worker public domain.** `worker-production-c770.up.railway.app` is pointless — workers don't accept HTTP — and is a small attack surface. Delete via Railway GraphQL.

3. **Keep the Redis volume.** Originally listed as a decision point; resolved to **keep**. Cost is negligible (~$0.01/mo) and it provides protection against losing queued tasks on Redis restart. Revisit only if we discover it's causing deployment friction.

4. **`/health/ready` readiness distinction.** Already covered in T2 above (the endpoint is part of the backend service change).

5. **Worker drain grace period.** Already covered in T2 via `drainingSeconds=60` — when Railway rolls a worker replica, it waits 60 seconds for in-flight tasks to finish before killing the container.

### T6 — CI/CD polish

1. **Railway deploy-wait step.** Add a new job to `.github/workflows/ci.yml` that runs after the current `backend-ci` job on main-branch pushes only. The job:
   - Polls the Railway GraphQL API for the latest `backend` deployment matching the current commit SHA
   - Waits up to 10 minutes for deployment status `SUCCESS`
   - Fails (red CI) if the deployment does not succeed
   
   This means merges to main only report green in GitHub when the backend is actually live, not merely when the CI suite passed. New secret: `RAILWAY_API_TOKEN` (workspace-scoped token).

2. **Cloudflare Pages git-connect — deferred.** The existing `deploy_vite_env_vars.md` guidance (secrets in Actions, build in Actions) is intentional and correct for the current CI flow. Switching to native Pages build would require moving secrets into Cloudflare, and the payoff is marginal. **Leave as-is.**

## Rollout plan

### Parallel execution model

The work is designed to be executed in **parallel worktrees with independent subagents**, using the `superpowers:dispatching-parallel-agents` and `superpowers:using-git-worktrees` skills. Each track has a dedicated worktree and subagent.

### Wave 1 (parallel)

Three subagents launched simultaneously in their own worktrees:

- **Worktree A / T1 — Celery chain refactor.** Branch `refactor/celery-chain`. Owns `analysis_steps.py`, creates `project_analysis_steps.py`, `pipeline_errors.py`, `_pipeline_utils.py`. Deletes `analysis_tasks.py`. Updates `routes/videos.py` and `routes/projects.py` for chain dispatch. Updates existing tests.
- **Worktree D / T6 — CI polish.** Branch `ci/railway-deploy-wait`. Owns `.github/workflows/ci.yml` only. Fully independent.
- **T4 preparation work:** lazy-import migration and `langgraph` removal can start in a worktree as well, but its final rebase must happen after T1 merges because both touch `analysis_tasks.py` imports. Marked as **W1.5** — start in parallel, rebase before merge.

### Wave 2 (serialized on Wave 1)

After T1 and T4 have landed and soaked on single-replica production for 24–48 hours (validating the chain refactor and memory cleanup before complicating the deployment shape), launch Wave 2:

- **Worktree B / T2+T5 — Infrastructure.** Branch `infra/multi-replica-topology`. Owns `startup.sh`, `Dockerfile.railway`, `railway.toml`, `database.py`, Redis service config, new `scripts/railway-service-config.sh`, `backend/app/main.py` (healthcheck endpoints). Creates the new `beat` service via Railway GraphQL. Deletes worker public domain. Applies Redis maxmemory.

### Wave 3 — validation

After Wave 2 lands:

- Confirm 2 backend replicas receive traffic via Railway logs
- Confirm `/health/ready` returns 200 under normal conditions and 503 when DB or Redis is unreachable (test by briefly pausing the Redis plugin)

- Run production smoke test (see Testing section below)

- Confirm Redis `maxmemory` is enforced via `redis-cli INFO memory` on the Redis service

## Testing & validation strategy

**Unit + integration tests.** Keep the existing `pytest` suite running green throughout. Tests that assert `analyze_video_task.delay(...)` or `analyze_project_task.delay(...)` are updated to assert that a `chain(...).apply_async()` is dispatched with the expected step signatures. Watchdog tests are updated so they no longer rely on the in-function `_is_cancelled` polling — they assert that the next step task's cancellation precheck handles the halt.

**Production smoke test script.** New file `scripts/production-smoke-test.py`:
- Hits production API with a test project + pre-uploaded fixture video
- Dispatches `POST /analyze`
- Polls `GET /analyze/status` until terminal state
- Asserts status reaches `"completed"` within 5 minutes
- Asserts all five `step_status` values transition to `"completed"`

Run manually after each wave. Becomes the "have we broken anything" quick check.

**Burst load test** (after T2 lands). Small `locust` or `vegeta` script:
- Fires 25 simulated analysis dispatches concurrently
- Measures per-step latency distribution
- Confirms no thread starvation (all tasks transition out of queue within 30 seconds)
- One-shot validation, not a regression suite

**Metrics to watch in Sentry + Railway logs:**
- `analyze_*_step` task duration distribution — should tighten around 20–40s per step (was: single 150s task distribution)
- Queue depth on the `analyze` queue — should stay below 50 at burst peak
- Failed task rate — at or below today's baseline
- Memory usage per service — backend and worker should each drop by ~100–200 MB post-T4

## Risks & mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| T1 refactor introduces subtle chain error-handling bug | Medium | High — broken analyses in production | Soak on single-replica for 24–48h before T2. Error handler idempotent. Keep existing per-step `except` blocks as a defense-in-depth layer. |
| Memory cleanup (T4) removes an import that some edge path silently relies on | Low | Medium — import error at runtime | Grep for every symbol before removing. Run full test suite. Smoke test production after merge. |
| Beat extraction causes a period where scheduled tasks don't fire (old worker still has `--beat`, new beat service not yet up) | Low | Low — missed watchdog cycle is recoverable | Deploy new beat service FIRST, verify it's firing, THEN deploy worker with `--beat` removed. |
| Multi-replica worker causes duplicate task execution | Very low | Medium | Celery's `task_acks_late + task_reject_on_worker_lost` already handles this correctly. Validated in Wave 3. |
| DB connection pool exhaustion under new topology | Low | High — backend 503s | Conservative pool sizes (see T2.DB section). Total ~58 connections under Postgres's 100 cap. |
| Railway API config script has a bug that misconfigures replicas | Medium | Medium | Script is idempotent and committed — review before running, apply to staging first if a staging env exists. |
| Hobby volume limit (5 GB, no backups) hit during rollout | Low | High — data loss risk | Not introduced by this spec, but called out so the backup-system spec is prioritized next. Current Postgres volume is 119 MB of 500 MB — plenty of headroom for the work in this spec. |
| User-visible downtime during T2 deploy | Low | Medium | `drainingSeconds`, healthchecks, and 2-replica rollout make this close to zero. Schedule T2 for off-peak hours anyway. |
